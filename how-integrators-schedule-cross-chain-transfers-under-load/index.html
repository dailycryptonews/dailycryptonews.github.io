How Integrators Schedule Cross-Chain Transfers Under Load

Integrators schedule cross-chain transfers by pricing routes, reserving liquidity and pacing submissions as congestion changes cost, delivery time and failure risk.

The Blockheight Editors·Oct 16, 2026 · 08:45 UTC·3 min read

Cross-chain integrators schedule transfers by matching each request to a route, available liquidity and the destination chain’s ability to settle it. Under load, they must weigh how quickly a route can execute against its price, capacity and chance of delay.

How does an integrator choose a route?

An integrator starts with the user’s source token, destination token and amount, then requests quotes for routes that can satisfy them. Mayan’s SDK documentation describes returning one quote per available route, with route type and expected output among the details an integrator can compare.

For the swap mechanics behind one route, see mayan bridge; the scheduling question is what happens when many such requests compete for execution. The integrator can compare quoted output and fees, then select a route that meets the user’s minimum acceptable amount and timing needs.

What changes when transfers arrive in a rush?

On-chain congestion can raise transaction costs and stretch confirmation times, while a route’s available liquidity can limit how much it can execute at once. An integrator can queue requests, group compatible work where the protocol permits, or route orders to other available liquidity; each choice trades speed against cost or execution certainty.

In Mayan’s documented Swift flow, drivers compete in an on-chain auction to execute orders. That model makes the quoted result and the execution opportunity distinct: a quote describes a proposed route, while the auction determines which driver takes the order.

How should an integrator pace submissions?

A scheduler should track each order from source-chain submission through destination delivery, and avoid treating a submitted transaction as a completed transfer. Mayan’s SDK offers a transaction status endpoint with states including in progress, completed and refunded, illustrating why integrators need a status check as well as a submission record.

A practical queue can prioritize requests using a few inputs:

  • Route capacity: whether the route can cover the order’s amount.
  • Quoted output: whether the minimum received still meets the user’s instruction.
  • Chain conditions: whether current fees and confirmation delays make submission worthwhile.
  • Order status: whether earlier work is pending, complete or refunded.

What should users expect during congestion?

Users should expect timing and final delivery to depend on both chains and the selected route, not just the first transaction. Integrators can reduce avoidable failures by refreshing quotes before submission and communicating when an order remains pending, but they cannot make congested chains settle instantly.

The next step is confirmation on the destination chain and an updated order status. Whether a specific transfer will clear quickly, or require a refund, remains unconfirmed until that status changes.
